# Wattwisely CPMS: review and testing manual

This manual is for the person who reviews the code and tests each feature by hand. It covers every module built so far, 1 to 19. For each module it says where the code is (branch, pull request, module document), which files to read and in which order, and a numbered test script with the result to expect at each step.

It builds on the documents that already exist and does not repeat them:

- [README.md](../README.md): what is in the repository and how the work is organised.
- [deploy/README.md](../deploy/README.md): installing on a server, backups, monitoring, the local trial.
- [docs/modules/](modules/): one walkthrough per module, with "Read the code in this order", "Running it" and "Tests" sections. The module sections below point into them.

## 1. Where the code is

Each module was built on its own branch with a pull request. Branches are named `NN-module/<slug>` (two-digit module number, then the slug of the module document), see [CLAUDE.md](../CLAUDE.md). Modules 1 to 8 are merged on `main`. Modules 9 to 19 are open pull requests (#28 to #39, which replaced #11 to #23 when the branches were renamed), **stacked**: each PR's base is the branch of the module before it, so each branch contains everything beneath it. Each module branch is built on the branch of the module before it and holds modules 1 to N, so the diff between two consecutive module branches is exactly one module. An annotated tag `module-NN` marks the commit that completed each module (`git tag -l 'module-*' -n1`).

## 2. Run the platform locally

The platform runs with Docker Compose; the charger simulator and the tests run with Node.js. The steps below come from the README, `deploy/README.md` and the "Running the platform locally" thread, and were checked from a clean checkout.

### 2.1 What you need

- Docker Desktop (macOS or Windows) or Docker Engine with the Compose plugin, with at least 4 GB of memory for Docker. Add about 1 GB for the monitoring profile (module 12).
- Node.js 22.12 or later and npm 11 (`npm install -g npm@11`). npm 10 refuses the lock file.
- An authenticator app on your phone (Google Authenticator, Microsoft Authenticator, 1Password): staff login requires two-factor.
- On Windows: run the shell scripts from Git Bash or WSL 2, and make sure Git does not convert line endings. `main` has a `.gitattributes` for that since PR #26; on an older checkout, run `git config core.autocrlf false` before cloning, or after cloning run `git rm -rq --cached . && git reset -q --hard` (this discards local edits).
- A free port 5432, or `POSTGRES_DEV_PORT=5433` in `deploy/.env` (PR #40) if a PostgreSQL already runs on your machine.

### 2.2 Choose the branch

Each branch holds everything beneath it, so the top of the stack runs every module at once.

| To test                         | Check out                                                                                                                                             |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Modules 1 to 8 only, as merged  | `main` with PR #40 merged in (on `main` alone the API and worker containers crash on start and the simulator drops its connection; PR #40 fixes both) |
| Modules 1 to N (N from 9 to 18) | the `NN-module/<slug>` branch of module N, for example `12-module/hardening-operations`                                                               |
| Everything, modules 1 to 19     | `19-module/driver-accounts-part-2` (PR #39's branch)                                                                                                  |

```sh
git clone https://github.com/findevdict-creator/wattwisely-cpms.git && cd wattwisely-cpms
git fetch origin
git checkout 19-module/driver-accounts-part-2            # or the NN-module/<slug> branch of the last module you want
git merge --no-edit origin/01-module/fix-local-trial    # PR #40's local-trial fixes; skip once PR #40 is merged. Keep this merge local, do not push it
```

Database migrations only move forward. Going from a higher module to a lower one needs a fresh database: `cd deploy && docker compose down -v` deletes all trial data, then start again as below.

### 2.3 Start everything

```sh
cd deploy
./scripts/install.sh --local      # writes deploy/.env with random passwords; add --force to replace an existing one
./scripts/up.sh --build           # builds the images from this checkout and starts everything; the first run takes several minutes
./scripts/seed-demo.sh            # demo tenants, users, sites, chargers, tariff, session, brand, plans, staff, drivers, cards
```

`up.sh` creates the database roles, runs every migration in `packages/db/migrations`, starts the containers, waits until they are healthy and unseals OpenBao. Run `up.sh --build` again after switching to a higher branch; the new migrations run on start. `./scripts/health.sh` checks every container and endpoint. `./scripts/logs.sh <service>` follows a service's logs (`api`, `worker`, `ocpp-gateway`, `keycloak`, ...). `./scripts/down.sh` stops everything and keeps the data.

### 2.6 The charger simulator

The simulator plays a charger from the command line. From the repository root, after `npm ci`:

```sh
npm run sim -- --url ws://ocpp.localhost/ocpp --identity WW-7KQ4M2XR9T            # a 1.6 charger; the demo chargers need no password
npm run sim -- --url ws://ocpp.localhost/ocpp --identity WW-7KQ4M2XR9T --tag DEMO-CARD-1   # holds an RFID card against plug 1 once booted (module 13)
npm run sim -- --url ws://ocpp.localhost/ocpp --identity WW-7KQ4M2XR9T --ocpp 2.0.1        # the same charger as an OCPP 2.0.1 station (module 18)
npm run sim -- --url ws://ocpp.localhost/ocpp --identity <id> --password <from the setup card>   # a charger you registered with a password
```

It boots, sends heartbeats and connector status, charges when the portal (or a card) says so with a meter value every 10 seconds, and answers stop, unlock, reset, availability and charging-profile commands. Leave it running in its own terminal while you test. Against `npm start` (development mode) use `--url ws://localhost:3100/ocpp` and set `OCPP_REQUIRE_TLS=false` in `apps/ocpp-gateway/.env`.

## 3. How to review a module

1. **Read the walkthrough first.** Every module document opens with the stories it covers and a "What changed since the module before" table, then "Read the code in this order", with one row per file and what it does. Follow that order; the module sections below give the short version.
2. **Diff one module at a time.** Each module branch holds modules 1 to N, so two consecutive module branches make a two-ended diff. Leave out the lock file and the migration snapshots, which are generated:

   ```sh
   git fetch origin
   git diff origin/08-module/tenant-branding origin/09-module/admin-portal-plans -- . ':!package-lock.json' ':!packages/db/migrations/meta'
   ```

   For module 19 the two ends are `origin/18-module/ocpp-201`, `origin/19-module/driver-accounts-part-1` (part 1) and `origin/19-module/driver-accounts-part-2` (part 2). On GitHub, the "Files changed" tab of each PR shows the same diff.

3. **Check the rules the code base enforces.** ESLint fails the build on any of them: classes only (no loose functions outside `main.ts`), one class per file, files of at most 200 lines, methods of at most 30 lines, 4 parameters, nesting depth 3, `controller → service → repository` in the API and `component → service → API` in the frontends, `snake_case` only in `*.dto.ts`.
4. **Check the things every module must have.** A migration pair (`NNNN_<name>.sql` for tables and policies, `NNNN_<name>_grants.sql` for what `wattwisely_app` may do), row-level security on every table with a `tenant_id`, `@RouteAccess` on every route, `If-Match` on every change to an existing row, an audit entry for every change, and a flow spec against Postgres for the API.
5. **Run the automated tests** (section 4), then the manual test script of the module. Report what you find on the module's PR; fixes go on the module's branch and PR, are merged forward into every module branch above it, and the `module-NN` tag is moved to the new tip.

## 4. Running the automated tests

```sh
npm ci
npm run lint                 # ESLint on every project; fails on any rule break
npm run build                # every app and package
npm test                     # unit tests everywhere; API, gateway and worker flow tests need TEST_DATABASE_URL
```

The flow tests run against a real Postgres: each spec file creates its own database and migrates it, exactly as `up.sh` does. Point `TEST_DATABASE_URL` at a superuser connection on a disposable Postgres 16, for example:

```sh
docker run --rm -d --name pg-test -e POSTGRES_PASSWORD=postgres -p 5440:5432 postgres:16
export TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5440/postgres
npx nx test api            # or: ocpp-gateway, worker, portal, driver, admin, db, pricing, session-engine, payments,
                           # payments-stripe, charger-sim, reports, billing, webhooks, load-management, messaging, file-storage, observability
```

Without `TEST_DATABASE_URL` the database-backed specs are skipped locally. CI (`.github/workflows/ci.yml`) starts a Postgres and runs lint, test and build on every push and PR, checks the shell scripts and the Compose file, and from module 12 runs the Prometheus alert-rule tests and a dependency audit. Every open PR is green.

Each module section below names the spec files that prove that module; `npx nx test <project> --testFile=<name>` runs one.

### Module 1: login with Keycloak

**Where:** `main`; `01-module/auth-keycloak`; [docs/modules/1-auth-keycloak.md](modules/1-auth-keycloak.md). Runs on every branch.

**What it adds.** Who is calling, and in which tenant: the portal logs in through Keycloak (code flow with PKCE, two-factor required for staff), the API checks every request's token and picks the tenant from the caller's own memberships, never from the URL. Also the repository skeleton (Nx, ESLint rules), the Docker Compose deployment and the Keycloak realm.

**Review, in this order.**

1. Portal start-up and login: `apps/portal/src/main.ts`, `core/config/runtime-config.loader.ts`, `app.config.ts`, `core/auth/auth.service.ts`, `auth-config.factory.ts`, `app.routes.ts`, `core/auth/auth.guard.ts`.
2. The realm: `deploy/keycloak/realm/wattwisely-realm.json` (brute-force lock after 5 failures, 30-minute idle session, 5-minute access tokens, events on, clients `wattwisely-portal` and `wattwisely-api`).
3. Portal after login: `core/tenant/workspace.guard.ts`, `user-loader.service.ts`, `core/auth/api-auth.interceptor.ts` (the token goes only to our API), `tenant-context.service.ts`, `layout/tenant-switcher.component.ts`.
4. API guards: `apps/api/src/common/auth/authentication.guard.ts` and its helpers (`bearer-token.extractor.ts`, `keycloak-token.verifier.ts`, `keycloak-key-set.provider.ts`), `common/tenant/tenant-context.guard.ts`, `tenant-membership.resolver.ts`, `common/auth/route-access.decorator.ts` (routes are private and tenant-scoped unless they opt out), `common/problem/problem-details.filter.ts` (RFC 9457 errors with a `code` and `request_id`).
5. Deployment: `deploy/docker-compose.yml`, `deploy/caddy/Caddyfile`, `deploy/scripts/*.sh`.

**Specs.** `apps/api/src/app.module.spec.ts` (the real API with a fake Keycloak: 401s, `/v1/me`, tenant switching, someone else's tenant is 404), `keycloak-token.verifier.spec.ts`, `tenant-membership.resolver.spec.ts`, `organization-claim.parser.spec.ts`; portal `tenant-context.service.spec.ts`, `api-auth.interceptor.spec.ts`.
