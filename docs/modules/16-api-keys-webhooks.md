# Module 16: API keys and webhooks

Module 2 gave every tenant an Owner with `api_keys:manage` and left a note: _API keys as audit actors: the Integrations module_. Module 9 then sold the feature as the plan module `api_keys`, "API keys and webhooks", on the Growth and Enterprise plans, with nothing behind it. This module builds it. A tenant **makes API keys** under Settings > API keys: a name, an optional expiry, and the permissions the key holds, chosen from what the maker may do for the whole company. The token is shown once; only its hash is kept. A system of the tenant's then **calls the API with the key** as a bearer token, within those permissions and in that tenant only, and everything it changes is in the audit log **as the key**, acting for the member who made it. The tenant also **adds webhook endpoints** under Settings > Webhooks: an https address and the events it wants to hear about. The worker **posts each event** there as signed JSON within seconds, **tries again** on a schedule when the endpoint does not answer, and the portal shows every delivery with its outcome.

Stories covered: Olivia makes the key "Fleet sync" with `sites:read`, `sessions:read` and `drivers:write`, copies the token from the one dialog that shows it, and Acme's fleet tool lists sites and sessions with it; the tool adds a driver and the audit log says API key "Fleet sync" did it, for Olivia; the tool asks for Volt Hotels' sites with Acme's key and gets 404, asks for `/v1/me` and gets 403, tries to create a site without `sites:write` and gets 403; Priya, an Integrator with `sites:read` and `api_keys:manage`, cannot make a key with `chargers:command`, and nobody can make a key that manages keys; Volt Hotels, on Starter, cannot make keys at all, and a key stops working the day a plan loses the module; the fleet tool goes wild and gets 429 after 600 requests in a minute while Olivia's own requests still go through; Olivia revokes the key and the next request with it is refused; Olivia adds `https://hooks.acme.example/wattwisely` for session.completed and alert.opened, presses Send test and sees the ping delivered with HTTP 200; a session completes and the fleet tool gets it, signed, within 15 seconds; the fleet tool is down for an hour and the delivery is tried again after 1, 5 and 30 minutes until it gets through; Olivia pastes `http://10.0.0.5/hook` and the API refuses an address inside the network; Theo, a Technician, sees neither page.

## What changed since module 15

| Before (module 15)                                                                                       | Now (module 16)                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| The audit log's actor was the signed-in account, or "Wattwisely (automatic)"                             | An action by a key is recorded with `actor_type = 'api_key'`, the key's id and the label `API key "Fleet sync"`; the portal's audit log shows an "API key" chip beside it                                                                                                                                                                                                                                                                                   |

## Design decisions

| Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A key is a bearer token, shown once, stored as a hash.** `wwk_` and 32 random bytes in base64url; the row keeps `sha256(token)` and the last four characters as a hint. A leaked database does not leak working keys. The prefix lets `AuthenticationGuard` tell a key from a Keycloak token without trying both, and lets a secret scanner recognise one                                                                                                                                                                                                  |
| **The key is found before the tenant is known.** The request carries no membership, so the usual tenant policy cannot apply yet. The lookup runs with `app.api_key_hash` set and no tenant, and the `api_keys_lookup` policy shows exactly the row with that hash, as the invitation token lookup does since module 2. Once found, the key's tenant is the request's tenant; an `X-Tenant-Id` header may only agree with it, and any other tenant is 404, as a tenant one is not a member of has always been                                                 |
| **A key holds a fixed set of permissions, never more than its maker had for the whole company.** `ApiKeyScopePolicy` checks each permission against the catalogue and against the maker's whole-tenant grants: a site-scoped Technician cannot give a key company-wide reach, and a key cannot hold `api_keys:manage`, because a key that makes keys would outlive its own revocation. The set does not follow later changes to the maker's roles; it says what the maker handed over, and the audit log names the key, so a reviewer can read the two apart |
| **A key acts for the member who made it.** `created_by` columns across the schema are account ids that are not null, so a key needs an account to write as; the maker's is the honest one, and the audit entry's actor is the key itself. Removing the member keeps the key working until it is revoked, because the systems that depend on it should not stop when someone leaves; the Owner sees "made by" on the list and decides                                                                                                                         |
| **Keys reach tenant routes only.** `/v1/me`, tenant selection, the admin console and anything else about a person or the platform answer 403 `api_key_not_allowed`. A key is a tenant's, so there is nothing to select and nobody to be                                                                                                                                                                                                                                                                                                                      |
| **Each key has its own budget for the minute, beside the address budget.** `RATE_LIMIT_API_KEY_PER_MINUTE` (600) per key id, on top of module 12's limits per client address, so one runaway integration cannot use up the address budget its tenant's people share, and a tenant's systems behind one address do not share one budget either                                                                                                                                                                                                                |
| **Revoked and expired keys stay.** The row keeps who revoked it and when, for the audit trail and the list. A revoked key is refused at once: the resolver's cache holds a key for 30 seconds, and revoking drops the tenant's entries, so "at once" is true on the instance that revoked and within 30 seconds on the others. The plan is read with the key, so losing the module stops every key of the tenant on the same terms                                                                                                                           |
| **Webhooks are an outbox per endpoint, filled by scanning, not by every module raising events.** Each endpoint has a `scanned_to` mark. The scan job reads the sessions and alerts that changed since the mark and queues one delivery per endpoint and event, unique on `(endpoint_id, event_id)` so a repeated scan queues nothing twice. Sessions, alerts and the gateway did not have to learn about webhooks; a new event type is one new source class. The mark lags real time by two seconds so a row written in the same instant is not missed       |
| **Every delivery is signed, and the timestamp is in the signature.** `Wattwisely-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<body>">` with the endpoint's `whsec_…` secret. A receiver checks the MAC and rejects anything older than five minutes, so a captured delivery cannot be replayed later. The event type and the delivery id ride in headers of their own, so a receiver can route before parsing                                                                                                                                    |
| **Retries follow a fixed schedule and then stop.** 1, 5 and 30 minutes, 2 and 12 hours: six attempts over about 14 hours, then `failed`. Any 2xx within ten seconds counts; anything else, a timeout or a refused connection is recorded on the delivery and counted on the endpoint as `failure_count`, which the list shows and a good delivery resets. Nothing pauses an endpoint by itself: the tenant can see it is failing and decides                                                                                                                 |
| **Addresses are https on the public internet, checked when saved and again when sent.** `WebhookUrlPolicy` refuses other schemes, credentials in the URL, `localhost`, names without a dot, and every private, loopback, link-local and metadata address, so a tenant cannot point the worker at the platform's own network. Redirects are not followed, for the same reason. `WEBHOOK_ALLOW_PRIVATE_URLS=true` lifts the host rule and allows plain http on a developer's machine, where the receiver is on the same host                                   |
| **A test is a real delivery.** Send test queues a `ping` event through the same table, worker, signature and retries as any other, so what the tenant sees in the deliveries list is what their receiver will get                                                                                                                                                                                                                                                                                                                                            |
| **The secret is readable by `api_keys:manage`, the key never is.** A webhook secret must be put into the receiver's configuration and is useless without the body it signs, so the portal shows it on request. A key gives access on its own, so it is shown once and never stored                                                                                                                                                                                                                                                                           |
| **Every change is a versioned write with an audit entry.** `If-Match` as everywhere since module 2. `api_keys.created`, `api_keys.updated`, `api_keys.revoked`, `webhooks.created`, `webhooks.updated`, `webhooks.deleted`, with the key's permissions and the endpoint's address and events in the before and after                                                                                                                                                                                                                                         |

| ----------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/api-keys`                  | `api_keys:manage` (tenant) | Every key, newest first, with `key_hint`, `permissions`, `created_by`, `last_used_at`, `expires_at`, `status` (`active`, `expired`, `revoked`); never the token                                                                                                                                             |

| `DELETE /v1/api-keys/{id}`          | `api_keys:manage` (tenant) | `If-Match`; revokes, 200 with the key; the row stays; 409 `api_key_revoked` when already revoked                                                                                                                                                                                                            |
| `GET /v1/webhooks`                  | `api_keys:manage` (tenant) | The endpoints with their `secret`, `event_types`, `is_active`, `failure_count`, `last_delivery_at`                                                                                                                                                                                                          |
| `GET /v1/webhooks/event-types`      | `api_keys:manage` (tenant) | The catalogue: `key`, `label`, `description`, `subject`                                                                                                                                                                                                                                                     |
| `GET /v1/webhooks/{id}`             | `api_keys:manage` (tenant) | One endpoint; 404 `webhook_not_found`                                                                                                                                                                                                                                                                       |
| `GET /v1/webhooks/{id}/deliveries`  | `api_keys:manage` (tenant) | `limit` (50, up to 200); newest first, with `status`, `attempts`, `next_attempt_at`, `last_status_code`, `last_error`, `payload`                                                                                                                                                                            |
| `POST /v1/webhooks`                 | `api_keys:manage` (tenant) | `{ url, description?, event_types }`; 201 with the endpoint and its secret. 422 `webhook_url_refused` with the reason, 422 `webhook_event_unknown`, 409 `webhook_limit_reached` at ten                                                                                                                      |
| `PATCH /v1/webhooks/{id}`           | `api_keys:manage` (tenant) | `If-Match`; `{ url?, description?, event_types?, is_active? }`                                                                                                                                                                                                                                              |
| `DELETE /v1/webhooks/{id}`          | `api_keys:manage` (tenant) | `If-Match`; 204; the deliveries go with it                                                                                                                                                                                                                                                                  |
| `POST /v1/webhooks/{id}/test`       | `api_keys:manage` (tenant) | 202 with the pending `ping` delivery the worker will send                                                                                                                                                                                                                                                   |
| Any tenant route, with a `wwk_` key | the key's permissions      | 401 `api_key_invalid`, `api_key_expired`, `api_key_revoked`; 403 `module_not_in_plan`, `api_key_not_allowed` (no tenant, or platform), `permission_denied`; 404 `tenant_not_found` for another tenant's `X-Tenant-Id`; 429 `rate_limited` past the key's budget                                             |

A stale `If-Match` is 409 `version_conflict`, a missing one 428, as everywhere.

A delivery is `POST <url>` with `Content-Type: application/json`, `User-Agent: Wattwisely-Webhooks/1.0`, `Wattwisely-Event: <type>`, `Wattwisely-Delivery: <id>` and `Wattwisely-Signature: t=<unix seconds>,v1=<hex>`, where the hex is HMAC-SHA256 over `<t>.<raw body>` with the endpoint's secret. The body is `{ "id", "type", "occurred_at", "tenant_id", "data" }`; `data` is the session or the alert in the shape of the API's own answers, in snake_case. A receiver answers any 2xx within ten seconds; `WebhookSignature.verify` in `packages/webhooks` shows the check in a dozen lines.

## Running it

Apply the migrations as always (`npm run db:migrate` or `./scripts/up.sh`, which runs them). New settings: the API's `RATE_LIMIT_API_KEY_PER_MINUTE` (600) and `WEBHOOK_ALLOW_PRIVATE_URLS` (false; the local `.env.example` sets it true so a receiver on your own machine works), the worker's `WEBHOOK_INTERVAL_MS` (15 s), `WEBHOOK_ALLOW_PRIVATE_URLS` and `RETENTION_WEBHOOK_DELIVERIES_DAYS` (30). `seed-demo.sh` gives Acme Charging the key "Demo fleet tool" with `sites:read`, `chargers:read` and `sessions:read`; its token is `wwk_demo-fleet-tool-0000000000000000000000000000` and the script prints it.

1. Log in to the portal as `owner@acme.test` and open **Settings > API keys**: the demo key is there with its hint. Call the API with it: `curl -H "Authorization: Bearer wwk_demo-fleet-tool-0000000000000000000000000000" http://localhost:3000/v1/sites` answers Acme's sites; `/v1/me` answers 403, and `/v1/sites` with `X-Tenant-Id` of Volt Hotels answers 404. Open the **Audit log**: nothing yet, reads are not audited.
2. Make a key of your own with `drivers:write`, copy the token from the dialog, and `POST /v1/drivers` with it. The audit log shows the entry with the "API key" chip and your name as the member it acted for.
3. Revoke the key and call again: 401 `api_key_revoked`.
4. Run a receiver on your machine (`npx -y http-echo-server 4000`, or anything that prints requests) and add `http://localhost:4000/hook` under **Settings > Webhooks** with session.completed and alert.opened; this works locally because `WEBHOOK_ALLOW_PRIVATE_URLS=true`. Press **Send test**: within 15 seconds the receiver prints the ping with its headers, and the deliveries list shows HTTP 200.
5. Start and stop a charge with the simulator (`npm run sim`, as in module 5): the receiver gets `session.completed`, signed. Stop the receiver and start another charge: the delivery stays pending with the connection error, is tried again after a minute, and the list shows the attempts.
6. Log in as `multi@demo.test` in Volt Hotels (Starter): the two pages say the module is not in the plan, and `POST /v1/api-keys` answers 403 `module_not_in_plan`.

| What                                                                                            | Where                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OAuth clients, scopes negotiated per request, short-lived tokens                                | A bearer key with a fixed set of permissions is what an operator's own systems need now; Keycloak can issue client credentials later, with the same `RequestAuth` behind them |
