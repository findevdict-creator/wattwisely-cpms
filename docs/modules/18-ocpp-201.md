# Module 18: The OCPP 2.0.1 adapter

Since module 4 the gateway has spoken OCPP 1.6J, and every charger row carries an `ocpp_version` that was always `1.6`. This module teaches the gateway **OCPP 2.0.1**, the version new chargers ship with and the one the Open Charge Alliance certifies against now. A charger says which versions it speaks when it opens its WebSocket; the gateway picks one, and from then on the connection runs through that version's **adapter**: the handlers for what the charger sends, the schemas its payloads must match, and the translator that turns a platform command into that version's CALL. Everything behind the adapter (sockets and leases, the session engine, the command queue, the message log, metrics, the API and the portal) is unchanged: a 2.0.1 station's charge is the same `charging_sessions` row with the same price, receipt and webhooks as a 1.6 charge point's. The simulator speaks both, so the flows are proven end to end against the real server. 2.1 is not in this module; the design makes room for it.

## What changed since module 17

| Before (module 17)                                                                                  | Now (module 18)                                                                                                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The gateway accepted the `ocpp1.6` subprotocol only; anything else was 400                          | `VersionCheck` takes the first subprotocol the charger offers that the gateway speaks (`ocpp1.6`, `ocpp2.0.1`), a charger that offers none at the version it last spoke, and refuses the rest. The handshake answers with the chosen one; the lease, the connection row and the charger row record it                        |
| One set of handlers, one `SchemaValidator`, and `V16CommandBuilder` called from the sender          | An `OcppAdapter` per version picked by `AdapterRegistry` from the connection's version; a `CommandTranslator` per version picked by `CommandTranslators`. The 1.6 code moved under `adapters/v16/` unchanged in behaviour; boot recording, heartbeats and meter arithmetic moved up a level because both versions share them |
| `charging_sessions` knew a transaction by the integer the platform handed out at `StartTransaction` | Migration 0031 adds `ocpp_transaction_ref`: the id a 2.0.1 station chooses for its transaction (up to 36 characters), unique per charger. The platform's own `ocpp_transaction_id` is still assigned, so reports and the API see no difference                                                                               |
| The gateway's errors spelt `FormationViolation` and `OccurenceConstraintViolation`, as 1.6 does     | `OcppCallError.codeFor(version)` spells them `FormatViolation` and `OccurrenceConstraintViolation` to a 2.0.1 station, which is what the standard renamed them to; every other code is the same in both                                                                                                                      |
| The simulator was a 1.6 charge point, in tests and on the command line                              | `ChargerMessages201` sends a station's messages in tests; `npm run sim -- --ocpp 2.0.1` runs the demo charger as a 2.0.1 station, one EVSE per connector, answering the platform's commands in 2.0.1 words. The 1.6 behaviour is untouched                                                                                   |

## Design decisions

| Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **The version is decided once, at the WebSocket upgrade, from `Sec-WebSocket-Protocol`.** That is how OCPP-J works: a charger lists what it speaks, the server answers with one, and nothing in the frames afterwards says which version they are. A charger that offers nothing (some firmware does) is taken at the version it booted with last time, so a known charger reconnects; an unknown charger offering nothing is refused as before, because guessing wrong would mean rejecting its first message with a confusing error                                                                                                                                                  |
| **An adapter is the inbound half of a version; a command translator the outbound half.** They are separate classes, not one, because the two paths depend on each other: a boot's follow-up queues commands through the sender, and the sender must not need the handlers to exist first. `AdapterRegistry` (handlers, schemas) serves `CallProcessor`; `CommandTranslators` (commands, replies) serves `CommandSender`. Both are keyed by `OcppVersion`, a type in `ocpp-contracts`, so a 2.1 adapter is two more classes and a third key                                                                                                                                             |
| **A 2.0.1 EVSE is a platform connector.** 2.0.1 splits a station into EVSEs (each charging one car) with one or more cables; the platform's connector, with its QR code, status and sessions, is the thing a driver plugs into, which is the EVSE. `connectors.ocpp_connector_id` holds the EVSE id and the `evse_id` column (there since module 3) is set to the same; the cable (`connectorId` inside the EVSE) is assumed to be 1. The connector is created from the first StatusNotification that names the EVSE, as module 4 does for 1.6                                                                                                                                         |
| **The connector's finer state comes from the transaction, not from StatusNotification.** 2.0.1's StatusNotification knows five words (Available, Occupied, Reserved, Unavailable, Faulted), while the portal shows preparing, charging, suspended and finishing. `Ocpp201Status` maps the five, and `V201ChargingStateApplier` refines Occupied from the transaction's `chargingState`: EVConnected is preparing (finishing once the transaction has ended), Charging is charging, SuspendedEV and SuspendedEVSE are the two suspended states. So the portal shows the same words for both versions                                                                                    |
| **One `TransactionEvent` handler, three steps.** Started, Updated and Ended are one message with an `eventType`, and a station may send them in any state the gateway did not expect: a Started twice after a reconnect, an Updated for a transaction the gateway never saw start, a token on an Updated because the car was plugged in before the card was shown. `V201TransactionStarter` finds the session by the station's id or opens it, `V201TransactionUpdater` records the token when it arrives late and the readings, `V201TransactionEnder` closes it once. Each event does all three in one transaction, so a reconnecting station's backlog lands in order               |
| **A session can start without a token.** 1.6 could not: StartTransaction carries the idTag. In 2.0.1 a Started with `CablePluggedIn` has none yet, so the session is opened with an empty `id_tag` and no driver, and the first event that carries a token fills them in through the same `TagPolicy` as Authorize (RFID cards, issued tags, `OCPP_ACCEPT_UNKNOWN_ID_TAGS`). The verdict goes back in the event's reply as `idTokenInfo.status`; a blocked card gets `Blocked` and the station is expected to stop                                                                                                                                                                     |
| **A remote stop names the transaction the way the station does.** `RequestStopTransaction` takes the station's own transaction id, not ours, so `V201CommandTranslator` looks up `ocpp_transaction_ref` for the command's session before building the CALL. A remote start carries a `Central` token (the platform's issued tag, as module 13 issues it) and a `remoteStartId` derived from the command id; the station echoes the token in its Started event, which is how the session is tied to the command that asked for it, exactly as in 1.6                                                                                                                                    |
| **Commands keep their platform names; only the words on the wire change.** The API and the worker still queue `remote_start`, `reset`, `set_charging_profile` and the rest. `OCPP201_ACTIONS` in the catalogue names the 2.0.1 call for each; `V201CommandBuilder` builds the payload: `Reset` `Immediate` for a hard reset and `OnIdle` for a soft one, `ChangeAvailability` with an `evse` or without one for the whole station, the load-management cap as a `ChargingStationMaxProfile` on EVSE 0 in watts and its clear by profile id. `Scheduled` (a reset the station will do when idle) and `Unknown` (a clear with nothing to clear) count as accepted, like module 17's rule |
| **Meter values are read into the same rows.** 2.0.1 sends a numeric `value` with an optional `unitOfMeasure` (unit and power-of-ten multiplier), and leaves out the measurand for the energy register. `V201MeterReader` applies the multiplier, fills the defaults (energy register, Wh, W, Percent) and hands the result to the shared `MeterReader`, so `meter_values` rows and the session's `energy_wh` are computed by one piece of code for both versions                                                                                                                                                                                                                       |
| **Messages a station must send are acknowledged, not refused.** `SecurityEventNotification`, `NotifyEvent`, `FirmwareStatusNotification` and `LogStatusNotification` are validated, logged in `ocpp_messages` and answered with an empty result, because a station that is told `NotImplemented` for a message the standard requires may give up on the connection. Nothing is recorded from them yet                                                                                                                                                                                                                                                                                  |
| **Schemas follow the Alliance's files, trimmed to what the gateway reads.** `validation/schemas/v201/` holds 27 schemas, every one taking `customData` and refusing unknown fields, with the enumerations spelt as the standard spells them. A wrong type is `TypeConstraintViolation`, a missing or unknown field `PropertyConstraintViolation`, naming the field, as for 1.6                                                                                                                                                                                                                                                                                                         |

## Running it

Apply the migration as always (`npm run db:migrate` or `./scripts/up.sh`, which runs it). No new settings: the gateway speaks both versions on the same address, `ws://ocpp.localhost/ocpp` in the Docker stack and `ws://localhost:3100/ocpp` during development.

1. Register a charger in the portal as in module 3 (or use the seeded `WW-7KQ4M2XR9T`) and start the simulator as a 2.0.1 station: `npm run sim -- --identity WW-7KQ4M2XR9T --password <from the setup card> --ocpp 2.0.1`. It logs `connected to … as ocpp2.0.1`, the boot's answer, and `connector 1: Available`, `connector 2: Available`. The charger page shows it online with its connectors Available; **Chargers > the charger** shows OCPP 2.0.1 as the version it booted with.
2. Press **Start charging** on connector 1: the simulator logs the `RequestStartTransaction`, a transaction id of its own choosing, `connector 1: Charging`, and a reading every ten seconds. The portal shows the connector preparing, then charging, the session's energy climbing, exactly as for a 1.6 charge point. Stop it from the portal: the simulator sends `TransactionEvent` Ended, the connector goes finishing then Available, and the session is priced and receipted as always.
3. With `--tag <an RFID card's tag>` the station authorises the card at boot and charges on connector 1; the session's driver is the card's.
4. Run the same simulator without `--ocpp`: it is a 1.6 charge point again, and the charger row shows 1.6. A charger connects at whichever version its firmware offers; the platform does not need to be told in advance.
5. The load-management cap of module 17 reaches a 2.0.1 station as `SetChargingProfile` with a `ChargingStationMaxProfile`; the simulator logs `power cap set to … W` either way.

## Not in this module

| What                                                                                                             | Where                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| OCPP 2.1                                                                                                         | A third `OcppVersion`, its subprotocol `ocpp2.1`, an adapter and a translator; 2.1 is 2.0.1 plus bidirectional charging, cost and tariff messages, and a few renamed fields, so most of `adapters/v201/` would be shared |
| Security profiles 2 and 3: TLS client certificates, `CertificateSigned`, `SignCertificate`, `InstallCertificate` | Chargers connect with basic auth over TLS (profile 1), as in module 4; certificates need a CA the platform runs or trusts, and the certificate messages are a module of their own                                        |
| The device model: `GetBaseReport`, `NotifyReport`, `SetVariables`, `GetVariables`                                | The portal does not read or set a charger's variables yet; the messages are a report store and a page, and `NotifyReport` would join the acknowledged list first                                                         |
| More than one cable per EVSE, and EVSE-level status in the portal                                                | The cable is assumed to be 1; a second cable is a `connectorId` on the connector row and a mapping decision about what a QR code points at                                                                               |
| Matching a station's Started event to the remote start by `remoteStartId`                                        | The echoed `Central` token ties them, as in 1.6; `remoteStartId` is sent and could be stored on the command for a station that answers with a different token                                                            |
| 2.0.1 reservations, local authorisation lists, display messages, `TriggerMessage`, `DataTransfer`                | None of them is in the platform for 1.6 either                                                                                                                                                                           |
| Transaction `offline` flags and the station's own `totalCost`                                                    | Offline events are recorded by their timestamps already; the platform prices the session itself                                                                                                                          |
| ISO 15118 and the token types beyond RFID and `Central`                                                          | A token's type is accepted as sent and the `idToken` string goes through `TagPolicy`; plug-and-charge needs contract certificates, which belong with the security profiles                                               |
