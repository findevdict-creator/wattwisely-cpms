# Module 14: custom roles and the permission matrix

Module 2 gave every tenant the same five roles and left a note: _custom roles and the permission matrix screen, later, the tables are ready_. Module 9 then sold the feature as the plan module `custom_roles` with one permission, `custom_roles:manage`, and nothing behind it. This module builds it. A tenant on a plan with the module **shapes its own roles**: a name, a description and a chosen set of permissions, started from a built-in role or from nothing. Every tenant, whatever its plan, gets the **permission matrix**: one page that shows every role against every permission, so an Owner can see at a glance what a Technician may do before giving the role.

Stories covered: Olivia opens Team > Roles and permissions and reads, column by column, what each built-in role allows; she creates "Depot supervisor" from Technician plus `drivers:write` and `alerts:acknowledge`, gives it to Theo, and Theo's next request already carries it; she later takes `drivers:write` out of the role and Theo loses it on his next request, without anyone touching his membership; she tries to delete the role while Theo holds it and is told to move him first; Priya, who holds a custom "Role admin" role, cannot put `team:manage` into a role because she does not hold it herself; Mia, on the Starter plan, sees the matrix with the five built-in roles and a note that custom roles come with Growth; the audit log shows who created, changed and deleted which role, with the permissions before and after.

## What changed since module 13

| Before (module 13)                                                                                   | Now (module 14)                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roles` and `role_permissions` could only be read by the API; rows came from migrations              | Migration 0023 adds `version`, `created_by` and `updated_by` to `roles`, a unique index on a tenant's role names (case-insensitive) and the `roles_tenant_changes` and `role_permissions_tenant_changes` policies; migration 0024 grants `wattwisely_app` INSERT, UPDATE and DELETE on roles and INSERT and DELETE on role permissions |
| `GET /v1/roles` and `GET /v1/permissions` were the whole roles API                                   | `POST /v1/roles`, `PATCH /v1/roles/{id}` and `DELETE /v1/roles/{id}` for custom roles, behind `custom_roles:manage`; roles answer `version`, permissions answer `module_name`                                                                                                                                                          |
| The roles a tenant could give were the five built-in ones (and the Managed operator role, module 10) | The same five plus the tenant's own. Inviting, changing roles and the role-giving rule from module 2 work unchanged with custom roles: `RoleAssignmentPolicy` reads them from the same table                                                                                                                                           |
| Changing what a role allows meant a migration, for every tenant at once                              | A change to a custom role applies to everyone who holds it on their next request: the API drops their cached access when the transaction commits, as a membership change does (story ACC-03)                                                                                                                                           |
| The portal had no page that showed what a role allows                                                | **Team > Roles and permissions**: the matrix, every role against every permission, grouped by module with a lock on modules the plan lacks; New role, Edit and Delete for custom roles on plans with the module; a note on other plans                                                                                                 |

## Design decisions

| Decision                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Built-in roles stay built in.** The five roles and the Managed operator role are shared by every tenant and come from migrations, as module 2 decided. The API answers 409 `role_is_system` to a change or a deletion, and the database policies refuse it too, so no bug in the API can rewrite Owner for every tenant. An operator who wants "Technician plus one thing" starts a custom role from Technician |
| **Nobody puts a permission in a role that they do not hold for the whole company.** The same rule as giving a role (module 2), with the same code `role_exceeds_own_access`: otherwise a holder of `custom_roles:manage` could write themselves a role with `team:manage`, give it to a friend and reach past their own access. Roles are tenant-wide, so a site-scoped permission is not enough                  |
| **A role that someone holds cannot be deleted.** 409 `role_in_use` names how many people hold it (invited and active). Deleting it would silently take access away from people the deleter may not even see; moving them first keeps every change to a person's access in the audit log as `team.member_roles_changed`                                                                                            |
| **A changed role reaches its holders at once.** The transaction that saves the change also lists the holders; once it commits, their cached access on this API instance is dropped, and other instances see the change within 30 seconds, the same path as removing a member                                                                                                                                      |
| **Names are unique per tenant, built-in names included.** Two roles called Technician in one invite dialog would be a trap. The database index covers the tenant's own roles; the API also checks against the built-in names, case-insensitively, and answers 409 `role_name_taken`                                                                                                                               |
| **Locked permissions can still be put in a role.** A permission whose module the plan lacks is shown with a lock and does nothing until Wattwisely adds the module (module 9's rule). Roles stay as they are across a plan change; a tenant that leaves Growth keeps its custom roles, they only cannot be changed until the module is back                                                                       |
| **The matrix is for everyone with `team:read`.** Knowing what a role allows is part of giving it. Only `custom_roles:manage` on a plan with the module turns the page from a table into an editor                                                                                                                                                                                                                 |
| **A role allows at least one thing.** An empty role has no use and would confuse the role-giving rule; the API answers 400 to an empty list                                                                                                                                                                                                                                                                       |

## Read the code in this order

### 1. The database: `packages/db`

| Step | File                                      | What it does                                                                                                                                                                                                                                             |
| ---- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `src/schema/roles.table.ts`               | `version`, `created_by`, `updated_by`; `roles_tenant_name_unique` on `(tenant_id, lower(name))` where `tenant_id` is set; `roles_tenant_changes`: the app role may insert, update and delete rows that are not system roles and carry the current tenant |
| 2    | `src/schema/role-permissions.table.ts`    | `role_permissions_tenant_changes`: the same for the permissions of the tenant's roles. Module 2's `*_visible` policies still show system rows to everyone                                                                                                |
| 3    | `migrations/0023_custom_roles.sql`        | Generated from the schema                                                                                                                                                                                                                                |
| 4    | `migrations/0024_custom_roles_grants.sql` | INSERT, UPDATE, DELETE on `roles`; INSERT, DELETE on `role_permissions`. Migration 0001 had said this would come with custom roles                                                                                                                       |

### 2. The API: `apps/api/src/modules/roles`

| Step | File                                | What it does                                                                                                                                                |
| ---- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `roles.controller.ts`               | The routes: reads with `team:read`, writes with `custom_roles:manage` and `If-Match`                                                                        |
| 2    | `role-permission.policy.ts`         | The pure rule for a role's permissions: every key exists, and the actor holds each one for the whole company. Answers the keys cleaned, each once           |
| 3    | `role-changes.service.ts`           | Create, update and delete: the name check, the version check, the permissions replaced as a whole, the audit entry, then the holders' cached access dropped |
| 4    | `roles.repository.ts`               | Reads as before, plus insert, update at a version, remove, `setPermissions` and `findHolderAccountIds`                                                      |
| 5    | `role-errors.ts`                    | `role_not_found`, `role_is_system`, `role_name_taken`, `role_in_use`, `permission_unknown`, `role_exceeds_own_access`                                       |
| 6    | `roles.service.ts`                  | Reads: the list with member counts (built-in roles first, then the tenant's own by creation), one role, the catalogue with `module_name` and `is_locked`    |
| 7    | `../team/role-assignment.policy.ts` | Unchanged: it already reads every role the tenant can see, so a custom role is given like a built-in one, under the same rule                               |

### 3. The portal: `apps/portal/src/app/features/team`

| Step | File                                      | What it does                                                                                                                                                                                                                |
| ---- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `team.routes.ts`                          | `/team` and `/team/roles`, both for `team:read`; the Team page links to the roles page                                                                                                                                      |
| 2    | `permission-matrix.ts`                    | Groups the catalogue by module, in the catalogue's order, and answers whether a role holds a permission                                                                                                                     |
| 3    | `roles.component.*`                       | The matrix: a sticky first column of permissions, one column per role with its member count; New role, Edit and Delete when `custom_roles:manage` is held and the module is in the plan; the lock on modules the plan lacks |
| 4    | `role-form.ts`, `role-dialog.component.*` | Name, description, "Start from" a role, and the permissions ticked one by one or a module at a time; locked modules are marked                                                                                              |
| 5    | `../../core/api/team-api.service.ts`      | `listPermissions`, `createRole`, `updateRole` and `removeRole`, the last two with `If-Match`                                                                                                                                |

### 4. Endpoints

| Endpoint                | Permission                     | Notes                                                                                                                                                                                                                                          |
| ----------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/roles`         | `team:read`                    | Built-in roles, then the tenant's own; each with `permissions`, `member_count` and now `version`                                                                                                                                               |
| `GET /v1/permissions`   | `team:read`                    | The catalogue; each entry now has `module_name` besides `module` and `is_locked`                                                                                                                                                               |
| `POST /v1/roles`        | `custom_roles:manage` (tenant) | 201; `name` (1–60), `description` (to 300), `permissions` (1 or more keys). 422 `permission_unknown`, 403 `role_exceeds_own_access`, 409 `role_name_taken`; 403 `module_not_in_plan` on a plan without the module                              |
| `PATCH /v1/roles/{id}`  | `custom_roles:manage` (tenant) | `If-Match` (428 without it, 409 `version_conflict` when stale); only the fields sent change; `permissions` replaces the set. 409 `role_is_system` for a built-in role. Everyone holding the role has the new permissions on their next request |
| `DELETE /v1/roles/{id}` | `custom_roles:manage` (tenant) | `If-Match`; 204; 409 `role_in_use` while anyone, invited or active, holds it; 409 `role_is_system`                                                                                                                                             |

Every change is in the audit log: `roles.created`, `roles.updated` and `roles.deleted`, with the name, description and permissions before and after. Giving a custom role to someone is `team.member_roles_changed`, as before.

## Running it

Apply the migrations as always (`npm run db:migrate` or `./scripts/up.sh`, which runs them). Nothing else to configure. Acme Charging is on Growth in the demo data, which includes custom roles; Volt Hotels is on Starter and sees the matrix read-only. `seed-demo.sh` adds one custom role to Acme Charging, "Depot supervisor", held by nobody, so it can be given, changed and deleted:

1. Log in as `owner@acme.test`, open **Team > Roles and permissions**. The matrix shows the five built-in roles, the Managed operator role and Depot supervisor.
2. Give Depot supervisor to Theo from the Team page (Change roles). Log in as `tech@acme.test` in another browser: the Drivers page now offers Add driver.
3. Back as Olivia, edit the role and take `drivers:write` out. Theo's next page load no longer offers it.
4. Try to delete the role: the button is greyed out while Theo holds it, and the API answers 409 `role_in_use` to anyone who tries anyway.

To see the locked state, log in as `multi@demo.test`, switch to Volt Hotels and open the same page.

## Not in this module

- Site-scoped custom roles as such: a custom role is given for the whole company or for chosen sites exactly like a built-in one; the permissions it holds are the same everywhere.
- Copying a role to another tenant, or roles Wattwisely staff shape for a tenant from the admin console.
- A role column on the Team page's filters (the API's `GET /v1/members?role_id=` already exists).
- Permissions on single sites or chargers inside a role, and permissions with conditions (amount limits for refunds live with the payments module).
- Hiding the Managed operator role from the matrix of a tenant that is not managed: it is a built-in role and is shown like the others, with no members.
